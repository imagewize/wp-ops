# Publishing wp-ops WordPress tools as a WP-CLI package

**Status:** evaluation, nothing implemented.
**Date:** 2026-08-21.
**Supersedes:** the Mistral draft of the same filename, whose compatibility
table was largely fabricated. [Corrections](#corrections-to-the-previous-draft)
records what was wrong, because the conclusions built on it are still
circulating.

Whether the PHP under `wp-cli/` should ship as a `wp package install`-able
WP-CLI package. Short answer: one file qualifies today, the rest either
aren't PHP or would be actively harmed by the packaging.

For the Trellis-side equivalent of this question — Ansible roles and
`trellis-cli` plugins — see
[`trellis-extensions-evaluation.md`](trellis-extensions-evaluation.md). That
path is cheaper and has better evidence behind it.

## The verified inventory

The `wp-cli` catalog category holds **16 commands: 5 PHP, 11 Bash.** Repo-wide
there are 11 PHP files, of which 5 are under `wp-cli/`.

Exactly **one file in the repository uses the WP-CLI API**:

```php
// wp-cli/content-creation/wp-cli-pattern-validate.php:54,61,401
if ( ! defined( 'WP_CLI' ) || ! WP_CLI ) { return; }
class Pattern_Validate_Command extends WP_CLI_Command { ... }
WP_CLI::add_command( 'pattern validate', array( $_cmd, 'validate' ) );
```

Every other file scores zero `WP_CLI` references:

| Path | Lang | `WP_CLI` refs | What it actually is |
| --- | --- | --- | --- |
| `content-creation/wp-cli-pattern-validate.php` | PHP | 34 | `WP_CLI_Command` subclass. Ships as-is |
| `content-creation/page-creation.sh` | Bash | — | Wrapper around `wp post create` |
| `content-creation/import-page-draft.sh` | Bash | — | Wrapper around `wp post create` |
| `security/scanner-targeted.php` | PHP (645 ln) | **0** | Standalone CLI PHP. ANSI `echo`, own arg parsing |
| `security/scanner-general.php` | PHP (830 ln) | **0** | Same |
| `security/scanner-wrapper.php` | PHP (95 ln) | **0** | Runs both scanners |
| `security/admin-user-create.sh` | Bash | — | Has SSH/remote support |
| `diagnostics/diagnostic-transients.php` | PHP (183 ln) | **0** | Standalone `wp eval-file` script |
| `diagnostics/transient-debug-browser.php` | PHP (327 ln) | **0** | **Emits HTML tables for a browser** |
| `diagnostics/list-posts-count.sh` | Bash | — | Wrapper around `wp post list` |
| `seo/*.sh` (7 files) | Bash | — | See below |
| `migration/*` (4 files) | **Markdown** | — | Documentation only. No code |

The SEO scripts deserve their own line. Two of the seven —
`redirect-audit.sh` (472 ln) and `schema-audit.sh` (335 ln) — contain **zero
`wp` invocations**. They `curl` a public URL and grep the HTML:

```bash
# wp-cli/seo/schema-audit.sh:20
# Requires: curl, grep
```

As WP-CLI commands they would require a WordPress installation in order to
audit a site that currently needs nothing but a URL.

## Corrections to the previous draft

The prior document's "Compatibility Assessment" table was the load-bearing
evidence for its entire recommendation and its 70-hour estimate. It appears to
have been generated by pattern-matching directory names.

| Prior claim | Reality |
| --- | --- |
| "`wp-cli/` contains ~20 WordPress-specific PHP scripts", "already 80% compatible" | 16 commands: 5 PHP, 11 Bash |
| `scanner-*.php` — "**90%**. Uses `WP_CLI` APIs, needs minor refactoring" | Zero `WP_CLI` references. Output layer and arg parsing would need a full rewrite |
| `diagnostics/*.php` — "**95%**. Already WP-CLI native" | Zero `WP_CLI` references. One of the two renders HTML for a browser |
| `migration/*.php` — "**85%**. Mostly WP-CLI compatible" | **No PHP files exist in `wp-cli/migration/`.** Four Markdown docs |
| `seo/*.php` — "**90%**. Uses WP-CLI patterns" | **No PHP files exist in `wp-cli/seo/`.** Seven Bash scripts |

The roadmap consequently budgeted 10 hours to "extract migration tools" and 8
hours to "extract SEO tools" — 18 of its 70 hours against files that do not
exist. The "2-3x the user base" estimate and "Claude Code uses wp-ops MCP
tools extensively" were asserted without measurement and should not be quoted
as findings.

What the draft got right: don't convert the whole repo (Ansible playbooks and
a Go binary are obviously not PHP subcommands), don't rename to `windfinder`,
and — in its own "Next Steps", contradicting its six-week roadmap — start with
one command as a proof of concept.

## The one real candidate

`wp-cli-pattern-validate.php` is already a WP-CLI command. Publishing it needs
a `composer.json` with `"type": "wp-cli-package"`, a repo, and a tag. That is
the whole job.

One thing to fix first. The command currently claims an unprefixed global
namespace:

```php
WP_CLI::add_command( 'pattern validate', ... );   // line 401
```

`pattern` is generic enough that a published package squatting it will collide
with something. Namespace it before publishing — `wp imagewize pattern-validate`
or similar. Renaming after release is a breaking change; renaming now costs one
line.

## Why packaging the scanners makes them worse

The scanners are the most broadly useful thing in `wp-cli/`, and packaging
them as a WP-CLI package would shrink their audience rather than grow it.

`wp-cli/security/README.md` documents running them:

- via `wp eval-file`
- via plain `php scanner-targeted.php /path/to/wordpress`
- via version-specific host binaries, e.g. `/opt/plesk/php/8.2/bin/php`
- via browser upload, on hosts with no shell at all

Those fallbacks exist because the target user is on cheap shared hosting
**without** WP-CLI. That is the whole point: a compromised site on a host where
you cannot install anything is exactly when you need a scanner. The scripts'
lack of `WP_CLI` coupling is a deliberate feature, not the 10% of technical
debt the prior draft described.

Making WP-CLI a hard dependency inverts this. If the scanners are ever
packaged, it has to be as an *additional* entry point wrapping the existing
standalone scripts, never as a rewrite of them.

---

## Recommendation

**Ship one package, measure, then decide.**

1. Rename `pattern validate` to a namespaced command. One line, do it
   regardless of whether anything is published.
2. Extract `wp-cli-pattern-validate.php` into its own small repo with a
   `wp-cli-package` `composer.json`. It works unmodified.
3. Publish, and see whether it gets installs. If it does, the next candidate
   is a thin WP-CLI front-end over the scanners — *wrapping*, not replacing,
   the standalone scripts.

Do not extract `diagnostics/`, `seo/`, or `migration/`. Two of those have no
PHP at all, and the SEO auditors are better off as they are.

The audience argument in the prior draft is also worth re-examining before
spending anything: the Trellis paths in
[`trellis-extensions-evaluation.md`](trellis-extensions-evaluation.md) reach a
community with demonstrated demand for exactly what this repo already has,
at lower cost.

## Appendix: reproducing the inventory

```bash
# Command counts by category
python3 -c "
import json, collections
d = json.load(open('go/internal/catalog/catalog.json'))
print(collections.Counter(x['category'] for x in d))"
# => {'scripts': 42, 'wp-cli': 16, 'trellis': 13, 'mcp-server': 3}  (74 total)

# Which wp-cli commands, and what language
python3 -c "
import json
d = json.load(open('go/internal/catalog/catalog.json'))
[print(x['script_path']) for x in d if x['category'] == 'wp-cli']"

# WP_CLI API usage across all PHP
for f in $(find . -name '*.php' -not -path './.git/*' -not -path '*/node_modules/*'); do
  echo "$(grep -c WP_CLI "$f")  $f"
done | sort -rn
```
